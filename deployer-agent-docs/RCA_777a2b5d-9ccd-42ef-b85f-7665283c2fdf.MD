## Verdict
This is a **CDN/prerender edge-cache problem, not an application bug** — your diagnosis is correct and the evidence below confirms it. The responsible layer is **Emergent's platform-managed Cloudflare crawler/prerender edge**, which is *not* inspectable or purgeable from the deployer toolset. **I have no tool to purge it** — that part must be done by Emergent Platform/Support (see action items).

## Evidence gathered
1. **Origin serves only the shell (expected).** A direct probe of the K8s origin `https://trade-brain-ai.emergent.host/industries/agriculture` returns `200` with the raw `<!doctype html>…` SPA shell. The origin never prerenders; bot HTML is generated/cached at the Cloudflare edge crawler layer. So the rendered-vs-shell distinction lives entirely at the edge.
2. **Backend SEO data path is healthy.** Over the last 24h the backend served the prerenderer's data calls — `/api/seo/page-data/<product>/<country>`, `/api/seo/product-hub/<product>`, `/api/product/<product>`, `/api/answers/html/...` — **all `200 OK`, zero errors/timeouts**, all from the crawler source IP `34.49.222.149`. When the renderer runs, the app feeds it fine. This rules out an app-side render error as the cause.
3. **No nginx manifest override exists** (platform default). Even if it did, with `frontend_type=cloudflare` nginx does not serve the public bot HTML — so the `cache-control: public, max-age=3600` header on the affected responses is **injected at the edge, not by your app**.
4. **Your own repro is decisive:** same URL + cache-busting query renders perfectly (3–5s, title/canonical/h1 present); plain URL returns a fast (0.19–0.56s) shell. A fast response = cache HIT of a previously stored bad snapshot. `/industries/agriculture` is fully static yet also shelled, which excludes "slow backend page-data" as the trigger. One path (`/corridors/india-to-uae`) self-healed on retry — consistent with its 1-hour snapshot TTL lapsing.

## Root cause (inferred — edge worker internals are not readable from this toolset)
A **failed / partial / raced prerender was cached as a `200` success** for the full edge TTL. The signature — static page also affected, fast cached shell, cache-bust renders correctly, one entry self-healing after ~1h — is the classic **"fall-through to index.html cached as success"** pattern.

**Why these 9 and why it correlates with yesterday's deploy:** the redeploy (2026-10-10T23:52→23:57Z) swapped the frontend bundle in R2 and flipped the KV version pointer that makes the new frontend live. Bot requests that landed **during that asset-swap window** rendered against a transient edge state (new/old asset mismatch or a hydration race), produced the bare shell, and that shell was stored with `max-age=3600`. Subsequent Googlebot hits serve the cached shell quickly until the TTL expires. Only the handful of paths crawled during the swap window got poisoned, which is why it is a small, semi-random subset of 446 URLs. Cache-busting creates a fresh cache key rendered *after* the swap, so it always looks correct.

## Answers to your four specific questions
1. **Purge the cache:** Not possible from the deployer agent — there is no CDN/prerender purge tool in this surface, and the Cloudflare crawler cache is platform-owned. It must be purged by Emergent Platform/Support. Absent a manual purge, each bad snapshot **self-evicts at its 1-hour TTL**, so the 9 paths will heal on their own within ~1h of when each was cached (one already did).
2. **Prerender TTL + fall-through:** Observed bot-HTML TTL is **`max-age=3600` = 1 hour** at the edge. The evidence strongly supports that **a prerender timeout/error/race falls through to the raw `index.html` and that shell is cached as a `200` for the full hour** — that is the root cause. Stopping failures from being cached requires an **edge-layer change** (do not cache non-rendered/shell responses as success; emit `no-store`/short TTL on fall-through; or only cache responses that pass a "has `<title>`/`<h1>`" gate). This cannot be controlled from the app.
3. **Is `cache-control: public, max-age=3600` app-controllable?** No. It is **platform-set at the Cloudflare crawler edge**. Your nginx has no override and does not serve bot HTML in this architecture, so you cannot change this header from the app.
4. **Prerender/build logs for render errors on these paths:** Prerendering is **request-time at the edge**, not part of the build — build logs contain no per-path render data (nothing to find there). The only app-visible signal is the backend data-fetch calls the renderer made, and those were all `200 OK` with no errors/timeouts (point 2 above). The failure therefore occurred inside the edge renderer (timeout/race during the deploy swap), which is not exposed to this toolset.
