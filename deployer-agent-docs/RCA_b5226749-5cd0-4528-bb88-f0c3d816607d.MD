## Separate backend defect found (NOT the shell cause — reported for correctness)
Backend logs show, twice (23:01:02 / 23:01:03 UTC):
`seo - WARNING - SEO matrix warm failed: '>=' not supported between instances of 'int' and 'Query'`

Root cause (located in deployed source):
- `backend/seo.py:329` `_warm_matrix_cache()` calls `seo_pages.matrix(limit=1000, force=True)` **directly** (not through an HTTP route).
- `backend/seo_pages.py:307` signature: `async def matrix(min_score: int = Query(0, ge=0, le=100), ...)`. FastAPI only resolves `Query(...)` defaults into real values when the function is invoked via the routing/dependency system. On a direct call, `min_score` stays a `Query` object.
- `backend/seo_pages.py:316` (and the force-path tail ~line 332) does `r["dataScore"] >= min_score` → `int >= Query` → TypeError.

Reproduced in an eph sandbox with the pinned `fastapi==0.110.1`:
```
type: Query
TypeError: '>=' not supported between instances of 'int' and 'Query'
```
(identical to the production log line).

**Why this is NOT the shell cause:** in the `force=True` path the full matrix is written to `db.seo_matrix_cache.replace_one(...)` *before* the throwing line executes, so the warm job still populates the cache each cycle (consistent with your 975-URL sitemap building correctly). The exception only drops the success log + return value. It is still a real bug and should be fixed, and it also means the cold-cache fallbacks in `_region_rows`/`_approved_rows` (which also call `matrix(...)` directly) would raise if ever hit on an empty cache.

**Fix (E1 to apply in source):** make `matrix()` safe to call directly — either give it a plain default (`min_score: int = 0`) and declare the `Query` binding in a thin route wrapper, or have internal callers pass `min_score=0` explicitly, or coerce at the top of `matrix()` (`if not isinstance(min_score, int): min_score = 0`). Apply the same to the other direct call sites.
