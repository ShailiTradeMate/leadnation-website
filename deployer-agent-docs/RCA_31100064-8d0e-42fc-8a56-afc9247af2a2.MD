# RCA — Vametra (trade-brain-ai) production: `/api/seo/matrix` hangs, sitemap truncated

Run investigated: `31100064-8d0e-42fc-8a56-afc9247af2a2` (active, redeploy, success, promoted 2026-10-31 20:46 UTC)
Frontend: Cloudflare · Tier: tier_0 (Starter) · Cluster: target-13

## Problem statement
Production only: (1) `GET /api/seo/matrix?limit=3` never responds (client times out >100s, http=000); (2) `GET /api/sitemap.xml` returns 200 but only ~157 of ~975 URLs, with `sitemap section answers/regions skipped: TimeoutError()`; (3) trade/OEC egress itself is fine. Preview is healthy because its Mongo already holds a warm `seo_matrix_cache`.

## What the evidence shows

### 1. The production `seo_matrix_cache` has NEVER been written
`mongo_query count seo_matrix_cache` → `collection_not_found`:
> collection "seo_matrix_cache" does not exist in database "vametra-whatsapp-test_database"
So there is no `matrix:all:all` document (no `at` timestamp — the collection itself is absent). Every request to `/api/seo/matrix` therefore takes the cold-rebuild path (`matrix()` rebuilds 440 rows).

### 2. The warm/rebuild job starts but never completes in the window
App logs:
- `20:45:34  apscheduler ... Added job "_warm_matrix_cache" to job store "default"` — scheduled on BOTH pods (also seen `×2`).
- `20:50:57  Running job "_warm_matrix_cache" ...` — the boot warm fires.
- **No matching completion / "rebuilt" / cache-written log line afterward.**
- Minutes later the rebuild is still issuing outbound duty lookups, e.g.
  `21:01:13 httpx GET https://wits.worldbank.org/.../reporter/826/partner/356/product/100630/... "HTTP/1.1 404 Not Found"` (and many identical WITS 404s at 20:54, 20:55, 20:57, 21:00).

The rebuild = 440 rows × `_duty_section` (WITS/World Bank) + `_buyer_section` + `_expo_section` + `_news_section` + `importer_detail`, concurrency-gated at semaphore 8. WITS returns **404 for most reporter/partner/product/year combinations**, and each 404 is still a full TLS round-trip to worldbank.org (no negative/short-circuit cache observed). Hundreds of these serialized behind an 8-wide gate take far longer than:
  - the client / Cloudflare edge timeout (~100s) → symptom 1 (http=000), and
  - the per-section `asyncio.wait_for(15s)` in `sitemap_xml` → `answers`/`regions`/`product-country` sections raise `TimeoutError` and are dropped → symptom 2 (157 vs 975 URLs).

Because the warm job itself never finishes inside the window, the cache row is never persisted, so the next request rebuilds from cold again — a permanent loop on this tier/dataset.

### 3. Not OOM, not a crash, not a restart
`get_pod_events`: both pods `Running`, `ready:true`, `restart_count:0`. No `OOMKilled`, no exit 137, no CrashLoop. Only boot-time `Startup probe failed 503` (normal while FastAPI boots) and a single `Liveness probe failed 503` at 20:47:48 that did **not** trigger a restart. So the cache failure is time/throughput-bound, NOT memory.

### 4. Resource ceiling (contributing)
`get_tier` tier_0: cpu request 50m / **limit 250m (0.25 vCPU)**, mem 200Mi / limit 512Mi, 2 replicas, ephemeral 1Gi, no HPA/VPA. A 440-row rebuild that opens hundreds of concurrent outbound HTTPS connections (TLS + JSON parse) is materially throttled at 0.25 vCPU, and **both replicas run their own scheduler**, so two concurrent rebuilds compete for the same CPU and hammer WITS in parallel. This widens the completion time further.

### 5. Edge timeout (expected, not a platform defect)
Frontend is served via Cloudflare. Cloudflare's edge enforces a ~100s origin-response limit (524). An inline rebuild that runs minutes will always be severed at the edge — matching the curl `http=000` after 100s+. There is no custom ingress misconfiguration to fix; the app must respond within the window.

## Production database — is it the intended one?
- Production `DB_NAME = vametra-whatsapp-test_database` (confirmed by `mongo_query`, which returns the resolved db name). This is a DIFFERENT database from preview (`leadnation` on cluster0.tpcdrfx). That is EXPECTED: production never shares the preview Atlas DB. `MONGO_URL`/`DB_NAME` are platform-managed SYSTEM secrets pointing at the app's own provisioned production Atlas DB, and they are **stable and persistent across redeploys** (data is migrated only on the initial deploy, never on redeploys). So forced trade-stats writes landing in prod but not in preview Atlas is correct behavior, not a bug.
- The `*-whatsapp-test_database` name is cosmetic (whatever the DB was named at initial provisioning); it does not mean data is ephemeral. Data persists.
- Masked connection host: the `MONGO_URL` value is stored encrypted and is never returned by tooling, so the Atlas host string cannot be printed from here. What is verifiable: `MONGO_URL` is set (non-empty) and resolves to DB `vametra-whatsapp-test_database`.
- Prod DB is partially warm, matrix cache cold: `duty_cache`=83, `trade_cache`=27, `expo_listings`=70, but `seo_matrix_cache` absent. This confirms the prod DB is the real, intended persistent DB — it simply has never had a successful matrix warm.

## Side observation (not the cause)
Kubelet health probes hit `GET /health` and the app returns **404** (route not registered at `/health`). Pods are nonetheless `Ready`, so this is tolerated, but the probe path appears mismatched to the app's actual health route — worth aligning separately.

## Root cause
The production `seo_matrix_cache` is empty, so `/api/seo/matrix` and three sitemap sections take the cold-rebuild path. That rebuild (440 rows, each doing slow World-Bank/WITS duty lookups that mostly 404 with no negative caching, 8-wide) cannot finish within the client/Cloudflare ~100s limit nor the sitemap's 15s per-section budget, and the background `_warm_matrix_cache` job likewise never completes in-window (run twice, once per replica, under a 0.25-vCPU tier_0 cap) — so the cache is never persisted and the cold path repeats forever. No OOM/crash involved.

## Suggested fixes
1. CODE (E1) — primary:
   - Serve `/api/seo/matrix` from cache only; never rebuild inline in the request. On a cache miss return quickly (stale/empty/202) and rebuild in the background.
   - Add negative caching / short-circuit for WITS 404s (and a per-call timeout) so repeated missing duty combos don't re-hit worldbank.org each rebuild.
   - Persist the matrix rebuild incrementally (write rows/progress as they complete) so a severed request or restart doesn't discard all work and the cache eventually lands.
   - Gate `_warm_matrix_cache` to a single replica (leader/lock) instead of running on both pods.
   - Ensure each sitemap section reads from the warm cache rather than doing live rebuild work under the 15s budget.
   - Align the health route with the probe path (`/health` currently 404s).
2. USER — Resources/tier (contributing): tier_0 caps CPU at 250m; a compute-/network-heavy matrix rebuild is throttled there. Raising the tier (Deployment Panel → Resources) will materially help the rebuild/warm job finish, but is a mitigation — without the code change above the inline endpoint can still exceed the ~100s edge limit.
3. No platform action required: the production DB is the correct, persistent app DB (different from preview by design); the Cloudflare ~100s edge timeout is expected behavior.
